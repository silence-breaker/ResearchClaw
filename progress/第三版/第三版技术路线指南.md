# ResearchClaw 第三版技术路线指南

> 版本：V3 技术路线
> 日期：2026-06-08
> 核查更新：2026-07-09
> 依据：`科研助手架构批判分析.md`、`progress/第二版/` 当前进度、`researchclaw/` 当前代码、用户补充的 V3 目标
> 当前真实进度：V3-M1 基本完成，V3-M2 完成配置/持久化但执行层尚未消费 policy；V3-M3/V3-M4 尚未完成；Gemini/Codex 尚未接入真实执行链路。

---

## 0. 结论先行

第三版的主线不是重新做一套科研架构，而是在 V2 已完成的研究流程上补三件事：

1. **三套 CLI 执行窗口打开**：ResearchClaw 不再只打开 Claude Code 窗口，V3 要同时支持 Claude Code、Codex CLI、Gemini CLI 三个独立执行窗口。
2. **按 phase 配置 CLI/model**：每个研究阶段都可以在 Settings 中选择使用 Claude / Gemini / Codex / mock，并落到后端真实路由。
3. **在想法评审后加入实验验证**：实验不是脱离 workflow 的旁路 execution layer，而是 Research Workflow Engine 中 `idea_review` 后、`summary` 前的正式 workflow phase，用于跑代码验证、采集结果、回灌 evidence。

第三版目标流程：

```text
研究契约
  → 文献侦察
  → 基线选择
  → 复现清单
  → 想法生成
  → 想法评审
  → 实验验证        [V3 新增]
  → 总结
```

第三版仍坚持 V2 红线：

- Research Workflow Engine 是唯一科研状态源。
- transcript/raw_log 只代表过程，不代表结论。
- artifact + gate 才能推进 phase。
- consult 是旁路，不直接进入主证据链。
- mock 保留为 CI 与回放底座。
- 所有 CLI/model 输出必须标注 provider、cli、model、source，不能让用户误以为 mock 或旁路对话是正式证据。

## 1. 关键约束：只使用 `API.md` 中 claude/codex/gemini 栏

### 1.1 API 白名单

ResearchClaw 在 V3 中只能读取 `API.md` 的 `# claude, codex, gemini` 栏配置。

该栏提供三类模型接入信息：

```text
claude_base_url = https://yunwu.ai
gemini_base_url = https://yunwu.ai
openai_base_url = https://yunwu.ai/v1
available_models = claude-haiku-4-5-20251001 ; gemini-3.1-flash-lite ; gpt-5.4-mini
```

实现时读取 API key，但不能在日志、SSE、artifact、raw_log、前端状态或错误信息中展示 API key。

### 1.2 三套 CLI，而不是 Claude Code 加载三种模型

V3 必须明确：Claude、Gemini、Codex 不是都通过 Claude Code 调用。

正确执行形态是：

| provider | 执行窗口/CLI | API.md 字段 | 模型 |
| --- | --- | --- | --- |
| `claude` | Claude Code CLI | `claude_base_url` | `claude-haiku-4-5-20251001` |
| `gemini` | Gemini CLI | `gemini_base_url` | `gemini-3.1-flash-lite` |
| `codex` | Codex CLI | `openai_base_url` | `gpt-5.4-mini` |
| `mock` | Mock adapter | 无 | mock |

所以 V3 的 adapter 层不是“一个 Claude Code adapter + 三个模型名”，而是：

```text
claudeCode adapter
codexCli adapter
geminiCli adapter
mock adapter
```

每个 CLI adapter 都负责：

- 启动自己的 CLI。
- 注入对应 base URL / API key / model。
- 捕获过程流。
- 生成 raw_log。
- 写出或解析结构化 artifact。
- 汇报 usage/cost。
- 向 SSE 标注 provider/cli/model/windowId。

### 1.3 安全边界

- 不读取 `API.md` 的 `# openclaw` 栏。
- 不读取任意系统 provider 环境变量作为 ResearchClaw 默认来源，除非是显式 `RESEARCHCLAW_*` override。
- Settings 不能让用户随意填 base URL/key；V3 Settings 只选择 `API.md` 白名单中已有 provider/model。
- API key 只存在后端进程环境与子进程环境中，不能进入前端和 artifact。

## 3. V3 架构目标

### 3.1 目标架构图

```text
Settings: Phase CLI Policy
        │
        ▼
Research HTTP API + SSE
        │
        ▼
ResearchOrchestrator  ← 唯一科研状态源
        │
        ▼
Phase Workflow
        │
        ▼
CliRouter
        │
        ├── ClaudeCodeAdapter  → claude code / API.md claude_base_url
        ├── GeminiCliAdapter   → gemini cli / API.md gemini_base_url
        ├── CodexCliAdapter    → codex cli / API.md openai_base_url
        └── MockAdapter        → fixture / CI / fallback
        │
        ▼
Structured Artifact + Raw Log + Usage
        │
        ▼
Gate / Evidence / UI
```

### 3.2 Phase 顺序

V3 正式 phase 顺序：

```js
const RESEARCH_PHASES = [
  'contract_draft',
  'contract_review',
  'literature_scouting',
  'baseline_selection',
  'baseline_reproduction_checklist',
  'idea_generation',
  'idea_review',
  'experiment_planning',
  'experiment_execution',
  'experiment_review',
  'summary'
];
```

新增实验阶段位于 `idea_review` 之后、`summary` 之前：

```text
idea_review
  → experiment_planning
  → experiment_execution
  → experiment_review
  → summary
```

### 3.3 为什么 experiment 要放进 workflow

之前文档把 experiment 写成单独的 `Experiment Layer`，容易让它看起来像旁路系统。根据当前 V2 架构和 V3 目标，正确做法是：

- experiment 是 Research Workflow Engine 的正式 phase。
- experiment artifact 由 orchestrator 管理。
- experiment gate 决定能否进入 summary。
- experiment raw log、commands、metrics、result 都进入同一个 evidence/store 体系。
- summary 必须消费 experiment evidence，不能绕过实验阶段直接总结。

可以有实验执行 CLI 或 runner，但状态推进必须属于 workflow，不能成为第二个状态源。

## 5. CLI Adapter 路线

### 5.1 当前 `route.js` 要升级为 CliRouter

当前 `route.js` 是：

```text
phase opted-in → primary Claude → fallback mock
```

V3 应升级为：

```text
phase → phaseCliPolicy → matched CLI adapter → structured result → fallback policy
```

建议新增或重构：

```text
researchclaw/adapters/cliRouter.js
researchclaw/adapters/claudeCode.js
researchclaw/adapters/geminiCli.js
researchclaw/adapters/codexCli.js
researchclaw/adapters/mock.js
```

### 5.2 Adapter 统一接口

三套真实 CLI 都实现同一接口：

```js
adapter.run({
  project_id,
  phase,
  prompt,
  schema,
  input_artifacts,
  workspace_dir,
  budget,
  eventBus
}) => {
  ok,
  adapter,
  provider,
  cli,
  model,
  artifact,
  raw_log,
  usage,
  error
}
```

consult 也可以支持 provider/CLI 选择，但 consult 不能降级 mock：

```js
adapter.consult({
  project_id,
  provider,
  cli,
  model,
  message,
  session_id,
  history
})
```

### 5.3 ClaudeCodeAdapter

继续沿用 `claudeCode.js` 的双通道模型：

- `stream-json` → SSE 过程流。
- `out.json` → 正式 artifact。
- raw transcript → raw_log。

### 5.4 GeminiCliAdapter

Gemini CLI V3 最小可行实现：

- 使用 `API.md` 的 `gemini_base_url` 和共享 API key 注入子进程环境。
- 使用 `gemini-3.1-flash-lite`。
- 过程输出进入 `raw_log` 与 SSE `cli_chunk`。
- 结构化输出写入 provider 专属 `out.json`，或由 adapter 从 CLI 输出中提取 JSON。
- schema 校验失败不得推进 phase。

### 5.5 CodexCliAdapter

Codex CLI V3 最小可行实现：

- 使用 `API.md` 的 `openai_base_url` 和共享 API key 注入子进程环境。
- 使用 `gpt-5.4-mini`。
- 重点服务代码/实验相关 phase：复现清单、实验规划、实验执行。
- 实验执行时必须记录 command、cwd、stdout/stderr、exit_code、produced_files。
- 对危险命令、超时、越权路径要 blocked，不要 mock 成功。

### 5.6 Fallback 策略

V3 fallback 必须按 phase/provider/CLI 配置：

```js
fallbackPolicy = {
  onCliUnavailable: 'mock' | 'blocked',
  onProviderUnavailable: 'mock' | 'blocked',
  onSchemaViolation: 'blocked',
  onTimeout: 'mock' | 'blocked',
  onOverBudget: 'blocked'
}
```

建议：

- 普通 workflow phase 可配置 mock fallback。
- `experiment_execution` 默认不要 mock fallback，失败应进入 blocked 或 experiment_failed。
- consult 永远不 mock fallback。
- summary 若输入含 mock evidence，必须标注“含 mock 输入”。

## 6. 实验验证 Workflow

### 6.1 实验阶段定位

实验阶段是 workflow 中用于验证想法的正式阶段。

插入位置：

```text
idea_review(pass)
  → experiment_planning
  → experiment_execution
  → experiment_review
  → summary
```

如果 `idea_review` 不通过，不进入实验。

### 6.2 `experiment_planning`

目标：把通过评审的 idea 转为可运行验证计划。

输入：

- contract artifact
- literature artifact
- baseline artifact
- reproduction checklist
- idea artifact
- idea_review artifact

输出 artifact：`experiment_plan`

建议 schema：

```js
experiment_plan = {
  hypothesis,
  idea_ref,
  baseline_ref,
  dataset_requirements,
  environment_requirements,
  commands,
  expected_outputs,
  metrics,
  success_criteria,
  failure_criteria,
  risks
}
```

默认 CLI：Codex CLI。

Gate：

- 必须引用一个 passed idea。
- 必须有可执行 command 或明确 manual step。
- metrics 必须与 contract metric 或 baseline metric 对齐。
- success/failure criteria 必须可判定。

### 6.3 `experiment_execution`

目标：跑代码验证。

输出 artifact：`experiment_run`

建议 schema：

```js
experiment_run = {
  plan_ref,
  status: 'passed' | 'failed' | 'blocked',
  commands_executed: [
    { command, cwd, exit_code, stdout_ref, stderr_ref, duration_ms }
  ],
  produced_files,
  raw_log_ref,
  metrics_observed,
  failure_reason,
  ended_at
}
```

默认 CLI：Codex CLI。

执行方式分两步：

1. V3 最小版：Codex CLI 在受控工作目录中生成/运行命令，记录 stdout/stderr。
2. 后续版：接入更严格 sandbox/runner。

Gate：

- 所有命令、输出、错误必须落 raw_log。
- exit_code 非 0 时不能伪装 passed。
- 没有 metrics_observed 时不能进入“实验支持结论”。
- 失败可以进入 `experiment_review`，但 summary 必须诚实说明失败。

### 6.4 `experiment_review`

目标：判断实验结果是否支持 idea claim。

输出 artifact：`experiment_review`

建议 schema：

```js
experiment_review = {
  run_ref,
  claim_support: [
    {
      claim_id,
      metric_ref,
      support_type: 'supports' | 'does_not_support' | 'inconclusive',
      rationale,
      evidence_excerpt
    }
  ],
  decision: 'accept_idea' | 'revise_idea' | 'reject_idea' | 'rerun_experiment',
  next_actions
}
```

默认 CLI：Claude Code。

Gate：

- 每条支持判断必须引用 experiment_run 或 metric。
- inconclusive 不能被 summary 写成 supports。
- `rerun_experiment` 应回退到 experiment_planning 或 experiment_execution。

### 6.5 Summary 的新约束

V3 summary 不能只基于 idea_review。

summary gate 必须检查：

- 是否存在 experiment_review。
- experiment_review 是否对主要 idea claim 给出 supports/inconclusive/does_not_support。
- 如果实验失败或 inconclusive，summary 必须明确写失败/不确定，不能写“验证通过”。

## 7. Evidence 与实验的关系

### 7.1 EvidenceReference 升级

V3 evidence 优先让实验引用落地：

```js
EvidenceReference = {
  id,
  claim_id,
  artifact_ref,
  artifact_type,
  content_path,
  excerpt,
  support_type: 'direct' | 'indirect' | 'contradicts' | 'inconclusive' | 'pending',
  provider,
  cli,
  model,
  raw_log_ref
}
```

### 7.2 实验优先证据

优先支持这些 evidence：

- `experiment_run.metrics_observed`
- `experiment_review.claim_support`
- `experiment_run.commands_executed.exit_code`
- `experiment_run.produced_files`
- `experiment_run.failure_reason`

文献证据可以支撑“相关工作/动机”，但实验结论必须优先来自 experiment artifacts。

```text
  │   ├── 实验执行: codex-cli / model
  │   ├── 实验评审: claude-code / model
  │   └── 总结: claude-code / model
  │
  └── Fallback Policy
      ├── CLI unavailable
      ├── provider unavailable
      ├── timeout
      ├── schema violation
      └── over budget
```

## 12. 风险与控制

### 风险 1：三套 CLI 输出格式不一致

控制：所有 adapter 必须输出统一 result shape，并由 schema gate 接管。CLI 响应文本不能直接进入 artifact。

### 风险 2：用户把 CLI 配到不适合的 phase

控制：Settings 给默认推荐和风险提示，但允许覆盖。artifact 记录实际 provider/cli/model，便于复盘。

### 风险 3：Codex CLI 跑代码带来安全风险

控制：V3 先限制工作目录、命令记录、timeout、raw log；危险命令需要 denylist/confirm；后续再接更强 sandbox。

### 风险 4：实验失败被 summary 美化

控制：summary gate 强制读取 experiment_review decision；failed/inconclusive 只能诚实表述。

### 风险 5：API key 泄露

控制：provider status 脱敏；日志/SSE/artifact 禁止 key；测试覆盖错误路径。

## 14. 第三版完成后的系统定位

第三版完成后，ResearchClaw 应被描述为：

> 一个以研究契约为入口、以 Research Workflow Engine 为唯一状态源、可按研究阶段选择 Claude Code/Gemini CLI/Codex CLI、能在想法评审后运行实验验证并把结果回灌到证据链的科研工作流编排器。

不应描述为：

- 只调用 Claude 的单模型工具。
- 用 Claude Code 加载 Gemini/Codex 的统一模型壳。
- 多 provider 随意填 key 的通用聊天平台。
- experiment 旁路系统。
- 不经过实验验证就宣称 idea 成功的总结器。

V3 的关键价值是：**让 CLI 选择变成可配置的工程能力，让实验验证成为正式 workflow，让总结建立在真实运行结果上。**
