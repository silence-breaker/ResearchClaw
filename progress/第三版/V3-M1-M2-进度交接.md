## 2. 为什么做 M1/M2

V3 的总目标是让 ResearchClaw 能按 phase 选择 **Claude Code / Gemini CLI / Codex CLI**，并在 idea_review 后跑实验验证。M1/M2 是配置地基：

- **M1**：让后端只读取 `API.md` 白名单栏，向前端暴露脱敏 provider 状态；同时探测三套 CLI 是否可执行。
- **M2**：让 Settings 不再用前端 demo 数据，而是把 **phase → provider/CLI/model** 的真实执行策略保存在后端，供后续 router 读取。

没有 M1/M2，M3 的 CliRouter 拿不到配置，M4 的过程流也无法区分来源。

## 4. 后端接口详细说明

### 4.1 `GET /system/providers`

**用途**：返回 `API.md` 中 `# claude, codex, gemini` 栏的脱敏配置。

**不返回**：API key、完整 URL（只返回 host）、`# openclaw` 栏内容。

**响应示例**：

```json
{
  "ok": true,
  "providers": [
    {
      "id": "claude",
      "configured": true,
      "baseUrlHost": "yunwu.ai",
      "models": ["claude-haiku-4-5-20251001"]
    },
    {
      "id": "gemini",
      "configured": true,
      "baseUrlHost": "yunwu.ai",
      "models": ["gemini-3.1-flash-lite"]
    },
    {
      "id": "codex",
      "configured": true,
      "baseUrlHost": "yunwu.ai",
      "models": ["gpt-5.4-mini"]
    }
  ]
}
```

**实现要点**：

- 调用 `getProviderStatus()`（`adapters/providers.js`）。
- `configured` 表示 base URL、API key、model 都齐全。
- 缺少 `API.md` 时全部返回 `configured: false, baseUrlHost: "", models: []`。
- 测试断言：响应 JSON 中不能出现 `apiKey`、`baseUrl`、openclaw 的 key。

### 4.2 `GET /system/cli-status`

**用途**：探测服务器上 `claude`、`gemini`、`codex` 三个二进制是否可执行。

**探测方式**：`sh -c 'command -v <cmd>'`，5 秒超时。不启动 CLI 本身，避免交互/耗时。

**响应示例**：

```json
{
  "ok": true,
  "clis": [
    { "id": "claude-code", "provider": "claude", "available": true, "command": "claude" },
    { "id": "gemini-cli", "provider": "gemini", "available": false, "command": "gemini" },
    { "id": "codex-cli", "provider": "codex", "available": false, "command": "codex" }
  ]
}
```

**实现要点**：

- 调用 `checkCliStatus()`（`settings/cliStatus.js`）。
- 支持注入 `checker(command)` 函数，便于测试和后续自定义探测逻辑。
- 单个 CLI 探测失败不会导致 endpoint 抛错或返回不完整列表。

### 4.3 `GET /settings/cli-policy`

**用途**：返回当前生效的 phase CLI policy，以及默认值和 fallback 值。

**响应示例**：

```json
{
  "ok": true,
  "policy": {
    "contract_draft": { "provider": "claude", "cli": "claude-code", "model": "claude-haiku-4-5-20251001" },
    "literature_scouting": { "provider": "gemini", "cli": "gemini-cli", "model": "gemini-3.1-flash-lite" },
    "...": "..."
  },
  "defaults": { "...": "..." },
  "fallbackPolicy": { "...": "..." }
}
```

**实现要点**：

- 调用 `resolveCliPolicy({ settingsDir: store.rootDir })`。
- `policy` = `defaults` 合并用户覆盖。
- `defaults` 和 `fallbackPolicy` 目前相同，都是写死的 `DEFAULT_PHASE_CLI_POLICY`。
- **隔离**：使用 `store.rootDir` 而不是 `process.cwd()`，避免测试/生产互相污染。

### 4.4 `PUT /settings/cli-policy`

**用途**：保存用户自定义的 phase CLI policy 覆盖。

**请求示例**：

```json
{
  "policy": {
    "literature_scouting": { "provider": "mock", "cli": "mock" },
    "idea_generation": { "provider": "gemini", "cli": "gemini-cli", "model": "gemini-3.1-flash-lite" }
  }
}
```

**成功响应**：`200`

```json
{
  "ok": true,
  "policy": { "合并后的完整策略" },
  "defaults": { "..." },
  "fallbackPolicy": { "..." }
}
```

**失败响应**：`400`

```json
{
  "ok": false,
  "errors": [
    "literature_scouting: cli gemini-cli does not match provider claude"
  ]
}
```

**实现要点**：

- 调用 `saveCliPolicy(body.policy || {}, { settingsDir: store.rootDir })`。
- 校验失败时**不写入任何内容**（原子性拒绝）。
- 只提交有改动的 phase；未提交的 phase 保持原值。
- 保存后只影响后续执行，**不修改历史 artifact**。

### 5.2 `settings/cliStatus.js`

```js
export const DEFAULT_CLI_COMMANDS = [
  { id: "claude-code", provider: "claude", command: "claude" },
  { id: "gemini-cli", provider: "gemini", command: "gemini" },
  { id: "codex-cli", provider: "codex", command: "codex" }
];

export async function checkCliStatus({ commands = DEFAULT_CLI_COMMANDS, checker = defaultChecker } = {}): CliStatusEntry[]
```

`CliStatusEntry` 结构：

```js
{ id: string, provider: string, available: boolean, command: string }
```

### 5.3 `settings/cliPolicy.js`

```js
// 默认策略常量
export const DEFAULT_PHASE_CLI_POLICY: Record<string, { provider, cli, model? }>

// V3 可配置 phase 列表（含未来 experiment phases）
export const V3_POLICY_PHASES: string[]

// 校验单个条目
export function validatePhasePolicyEntry(phase, entry, context = {}): string[]

// 校验完整/部分 policy
export function validateCliPolicy(partialPolicy, context = {}): string[]

// 读取生效策略
export function resolveCliPolicy({ settingsDir = cwd/.researchclaw, context = null } = {}): { policy, defaults, fallbackPolicy, context }

// 保存覆盖
export function saveCliPolicy(partialPolicy, { settingsDir, context = null } = {}): { ok: true, policy, defaults, fallbackPolicy } | { ok: false, errors }

// 单 phase 查询
export function resolvePhasePolicy(phase, options = {}): { provider, cli, model? } | null
```

`context` 形状：

```js
{
  providers: [
    { id: "claude", configured: true, baseUrlHost: "...", models: [...] },
    ...
  ]
}
```

如果未传 `context`，函数内部会调用 `getProviderStatus()` 自动构造。

## 6. 数据流

### 6.1 M1 数据流

```
API.md (# claude, codex, gemini)
    ↓
parseApiMd() / loadProviders()
    ↓
getProviderStatus() ──→ /system/providers

PATH 环境
    ↓
checkCliStatus() ──→ /system/cli-status

前端 Settings 页
    ↓
fetchProviders() + fetchCliStatus()
    ↓
渲染 Provider 卡片 + CLI 卡片
```

### 6.2 M2 数据流

```
API.md + 用户保存
    ↓
saveCliPolicy() 校验并写入 .researchclaw/settings.json
    ↓
resolveCliPolicy() 读取 defaults + 用户覆盖
    ↓
/settings/cli-policy 返回 effective policy

后续 M3 CliRouter
    ↓
resolvePhasePolicy(phase) → { provider, cli, model }
    ↓
spawn 对应 CLI adapter
```

## 8. 校验规则

1. `provider ∈ {claude, gemini, codex, mock}`
2. `cli ∈ {claude-code, gemini-cli, codex-cli, mock}`
3. `provider` 与 `cli` 必须匹配：
   - claude → claude-code
   - gemini → gemini-cli
   - codex → codex-cli
   - mock → mock
4. `mock` provider 不能指定 `model`
5. 非 `mock` provider 必须指定 `model`
6. `model` 必须在对应 provider 的可用 models 列表中
7. `phase` 必须属于 `V3_POLICY_PHASES`

## 11. 给 V3-M3 的接入指南

### 11.1 在哪里读取 policy

M3 的 CliRouter 应该在执行 workflow 前调用：

```js
import { resolvePhasePolicy } from "./settings/cliPolicy.js";

const entry = resolvePhasePolicy(phase, { settingsDir: store.rootDir });
// entry → { provider: "gemini", cli: "gemini-cli", model: "gemini-3.1-flash-lite" }
```

注意：因为 `resolvePhasePolicy` 默认使用 `process.cwd()/.researchclaw`，而生产/测试的 store rootDir 可能不同，**建议永远传入 `store.rootDir`**。

### 11.2 建议的 adapter 结构

参考现有 `adapters/claudeCode.js`，新增：

```
researchclaw/adapters/
  geminiCli.js   # spawn gemini <...>
  codexCli.js    # spawn codex <...>
  router.js      # 新：根据 phase policy 选择 adapter
```

`router.js` 可以替换或扩展现有的 `adapters/route.js`。当前 `route.js` 的接口是：

```js
export function createRoutingAdapter({ phases, primary, fallback, costTracker, eventBus })
```

M3 建议改为：

```js
export function createPolicyRouter({ store, eventBus, costTracker, adapters })
```

其中 `adapters` 按 provider 注册：

```js
{
  claude: new ClaudeCodeAdapter(...),
  gemini: new GeminiCliAdapter(...),
  codex: new CodexCliAdapter(...),
  mock: new MockModelAdapter(...)
}
```

### 11.3 adapter 输出统一 shape

无论哪套 CLI，最终必须输出统一结构：

```js
{
  ok: true | false,
  adapter: "claude" | "gemini" | "codex" | "mock",
  artifact: { ... },        // gated artifact
  raw_log: { ... },         // cli transcript
  usage: { ... },           // token/cost
  degraded?: boolean        // 是否 fallback 到 mock
}
```

### 11.4 artifact 来源标记

M4 要求 artifact/raw_log/SSE/usage 都记录 `provider/cli/model`。建议在 `producer` 中扩展：

```js
producer: {
  workflow: "...",
  adapter: "claude",
  cli: "claude-code",
  model: "claude-haiku-4-5-20251001"
}
```

但注意这会改动 `Artifact` schema，属于 B（Contract Owner）的 review 范围。

## 12. 已知问题与坑

### 12.1 Provider 未配置时 model 校验

当前 `validatePhasePolicyEntry` 在校验 model 时：

```js
const providerStatus = (context.providers || []).find((p) => p.id === entry.provider);
if (providerStatus && providerStatus.configured && !providerStatus.models.includes(entry.model)) {
  errors.push(...);
}
```

这意味着如果 `API.md` 未配置某个 provider（`configured: false`），用户仍可以把 phase 配成该 provider 的任意 model 并保存。这是有意设计：允许先配置策略再补 API.md。但如果 M2 验收要求更严格，可改为 provider 未配置时直接拒绝非 mock 策略。

### 12.2 Settings 文件位置与权限

`saveCliPolicy` 使用 `mkdirSync(settingsDir, { recursive: true })`。如果 store rootDir 在不可写位置，会抛错并由 server.js 的 `try/catch` 转成 500。生产部署时需要确保运行用户对 store rootDir 有写权限。

### 12.3 CLI 探测只是 PATH 检查

`checkCliStatus` 用 `command -v` 检查二进制是否存在，**不验证版本、不验证能否联网**。M3 的真实 CLI smoke 应该补充版本/登录状态检查。

### 12.4 前端 ModelSettings 没有组件渲染测试

目前靠 typecheck + build + 手验。`ModelSettings.tsx` 有 300+ 行，后续若要重构建议补 `@testing-library/react` 测试。

### 12.5 当前执行层仍忽略 policy

`orchestrator` 和 `route.js` 仍按 M2 逻辑执行：只有 `contract_draft` 在启用 Claude 时走真实 CLI，其余全部 mock。M3 的核心任务就是把这个硬编码路由替换成 policy 驱动的路由。

## 13. 架构红线遵守情况

| 红线 | 状态 | 说明 |

| 不改 OpenClaw 源码 | ✅ | 只改 researchclaw/ 内文件 |
| 不修改他人负责模块核心逻辑 | ✅ | 未改动 orchestrator/gates/contract schema |
